# **AWS MSK (Managed Streaming for Apache Kafka) - Complete Developer & Architect Guide**


## Part 1: Introduction to Kafka & MSK

### What is Apache Kafka?

Apache Kafka is a **distributed event streaming platform** used to build real-time data pipelines and event-driven systems. It is designed for **high-throughput**, **low-latency**, and **scalable** messaging between services or systems.

### What is AWS MSK?

**Amazon MSK (Managed Streaming for Apache Kafka)** is a fully managed service that makes it easy to set up, operate, and scale Apache Kafka on AWS without the overhead of managing the Kafka infrastructure yourself.

## Part 2: Key Terminology

| Term                   | Description                                                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Topic**              | A **logical unit** that represents a named stream of messages. Applications publish to and consume from topics.                                       |
| **Partition**          | A **physical unit** of storage for a topic. Each topic consists of one or more partitions that store messages in an ordered, immutable log.           |
| **Offset**             | The position of a message within a partition. Used for tracking read progress.                                                                        |
| **Broker**             | Kafka server that stores partitions and serves producers/consumers.                                                                                   |
| **Producer**           | Application that sends data (messages/events) into Kafka topics.                                                                                      |
| **Consumer**           | Application that reads data from Kafka topics.                                                                                                        |
| **Consumer Group**     | A set of consumers that work together to consume data from a topic's partitions without duplication.                                                  |
| **Replication Factor** | Number of copies of each partition for durability.                                                                                                    |
| **Message ID**         | A unique identifier included in each message (can be generated by the producer). Used for **idempotency** and **deduplication** at the consumer side. |
| **Partition Key**      | A key used by the producer to determine which partition a message should be routed to. Ensures ordering for messages with the same key.               |

## Part 3: Kafka/MSK Core Concepts

### Why Consumer Groups?

* **Scalability**: Multiple consumers in a group can read from different partitions of the same topic, enabling parallel processing.
* **Fault Tolerance**: If a consumer crashes, Kafka redistributes its partitions to other consumers in the group.
* **Load Balancing**: Partitions are evenly assigned among all consumers in the group.
* **No Duplication**: Each message is consumed by exactly one consumer in a group.

**Example:**
If you have a topic with 6 partitions and 3 consumers in the same group, each consumer will be assigned 2 partitions. Without a group, each consumer would process all 6 partitions, causing duplication.

### Partitioning

* Partitions are the **unit of parallelism** in Kafka.
* **How partitions are chosen:**

  * **Key-based partitioning:** `hash(key) % number_of_partitions` ensures all messages with the same key go to the same partition.
  * **Round-robin:** If no key is provided, Kafka balances messages across partitions.
  * **Custom partitioner:** Developers can create custom logic for assigning partitions.
* More partitions = higher throughput (more parallelism).
* **Caution:** Adding partitions after deployment may affect ordering guarantees.

### Role of Partition Keys

* **Producer-Side:**

  * Determines which partition a message is written to.
  * Ensures all messages with the same key (e.g., `transactionId`) are in order within a single partition.
* **Consumer-Side:**

  * Consumers don’t select partitions based on keys, but **partition keys guarantee that all related messages are processed by the same consumer in a group**.
  * Useful for stateful processing, e.g., aggregating all events of a specific transaction.
  * Allows building **idempotent logic** by using the key as a correlation ID.
* **Load Distribution:**

  * Well-distributed keys prevent hotspots (i.e., one partition handling the majority of traffic).
  * Poor key choice (e.g., a single static key) can overload one partition.

### Topics (Logical Unit)

* A **topic** is a logical abstraction—a name or category for a stream of messages (e.g., `payment-events`).
* Producers and consumers interact with topics, not partitions directly.
* A topic is divided into **partitions**, which are managed by Kafka under the hood.

### Partitions (Physical Unit)

* A **partition** is where Kafka **actually stores** messages on disk.
* Each partition belongs to **one topic** and is stored on a **Kafka broker**.
* Messages in a partition are **strictly ordered** and **append-only**.

### Brokers

* Kafka brokers store partitions and serve as the **backbone of the cluster**.
* In MSK, brokers are automatically provisioned across **multiple AZs** for fault tolerance.

### Consumer Group & Rebalancing

* Kafka assigns partitions to consumers in the same group.
* When a consumer joins/leaves or subscription changes, **rebalancing** occurs to redistribute partitions.
* Kafka uses algorithms like **Range**, **RoundRobin**, and **CooperativeSticky** (default in newer versions) for partition assignment.
* During rebalancing:

  * All consumers temporarily stop consuming.
  * The group coordinator reassigns partitions.
  * Consumers resume consumption from their new partitions.
* Rebalancing can be minimized using **Cooperative Rebalancing** which allows non-disruptive scaling by only reassigning changed partitions.

### Replication

* Each partition has one **leader** and multiple **followers** for high availability.

### Delivery Semantics

| Type          | Explanation                                               |
| ------------- | --------------------------------------------------------- |
| At Most Once  | May lose messages.                                        |
| At Least Once | Messages may be reprocessed; **idempotency** is required. |
| Exactly Once  | Complex, requires Kafka transactions.                     |

## Part 7: Partition Count Strategy & Consumer Parallelism

### How to Decide Partition Count?

**Factors:**

1. **Throughput needs** – Each partition has a max throughput (e.g., 5 MB/sec). For 50 MB/sec, use at least 10 partitions.
2. **Parallelism (Consumers)** – You can have up to one active consumer per partition in a group.
3. **Ordering constraints** – All events for a key (e.g., `transactionId`) must go to one partition.
4. **Future scalability** – Overprovision partitions to avoid repartitioning.

**Rule of Thumb Formula:**

```
partitions = max(
    (desired_throughput / throughput_per_partition),
    number_of_parallel_consumers
)
```

### Example

* **Scenario:** Payment events at 50 MB/sec.
* **Per partition capacity:** 5 MB/sec.
* **Consumers needed:** 5 instances.
* **Partitions:** `max(50/5, 5) = 10`.

### Consumer Model

* **10 partitions**, **5 consumer instances**.
* **Assignments:**

  * C1 → P0, P1
  * C2 → P2, P3
  * C3 → P4, P5
  * C4 → P6, P7
  * C5 → P8, P9

## Part 5: Scaling & Multi-AZ Strategy

* **Scaling a Single Microservice:** Payment service can run as 5 instances consuming from the same topic.
* **Consumer Group:** All 5 instances share the same `GroupId` (e.g., `payment-service-group`). Kafka ensures partition assignment.
* **Multi-AZ Deployment:** Spread consumers across 2-3 AZs (e.g., 2 in AZ-A, 2 in AZ-B, 1 in AZ-C).
* **Rebalancing:** If an instance fails, partitions are reassigned to other active instances.
* **Elastic Scaling:** Add or remove instances dynamically (e.g., via ECS/EKS autoscaling).

## Part 7: .NET Integration Example

### Producer Code

```csharp
var messageId = Guid.NewGuid().ToString();
var config = new ProducerConfig { BootstrapServers = "b-1.msk-cluster:9092" };
using var producer = new ProducerBuilder<string, string>(config).Build();

await producer.ProduceAsync("order-events", new Message<string, string>
{
    Key = "transaction123", // partition key to ensure order
    Value = $"{{ \"messageId\": \"{messageId}\", \"status\": \"created\" }}"
});
```

### Consumer Code

```csharp
var config = new ConsumerConfig
{
    BootstrapServers = "b-1.msk-cluster:9092",
    GroupId = "notification-service",
    AutoOffsetReset = AutoOffsetReset.Earliest
};

using var consumer = new ConsumerBuilder<Ignore, string>(config).Build();
consumer.Subscribe("order-events");

while (true)
{
    var result = consumer.Consume();
    Console.WriteLine($"Key: {result.Message.Key}, Value: {result.Message.Value}");
}
```

# Use Case of Partitions

## If I am taking pymentId as partition key and 1 million/sec request come with different paymentId then 1 million partitions will be there?
No — **1 million partitions will *not* be created** just because you have 1 million unique `paymentId`s per second.

Let’s break this down clearly:

---

### 🔹 Kafka Partitioning Logic (Reminder)

Kafka **does NOT** create one partition per key.

Instead, it uses a **fixed number of partitions per topic**, and then determines **which partition to send a message to** based on the key using this formula:

```
partition = hash(partitionKey) % numberOfPartitions
```

So if your topic has 100 partitions:

* Kafka takes the `paymentId`, hashes it, and maps it to one of the 100 partitions.
* Even if you get 1 million unique `paymentId`s per second, they will be **distributed across those 100 partitions**.

---

### 🔸 Example

* You define:

  ```bash
  kafka-topics.sh --create --topic payment-events --partitions 100 ...
  ```

* You produce:

  ```csharp
  Key = paymentId // unique every time
  ```

* Kafka will:

  * Hash each `paymentId`
  * Route each message to one of the 100 partitions
  * No new partitions are created dynamically

---

### ✅ Why This Is a Good Thing

* You don’t want 1 million partitions — Kafka brokers and consumers would **choke**.
* Partition count is a **scaling knob** you control — usually determined by throughput and parallelism needed.
* **More partitions = more parallelism**, but also more metadata, replication overhead, and consumer complexity.

---

### 🔹 Then How Many Partitions Should You Have?

That depends on:

| Factor             | Rule of Thumb                                        |
| ------------------ | ---------------------------------------------------- |
| Target throughput  | \~1 MB/s or \~10,000 msgs/sec per partition          |
| Consumer count     | One active consumer per partition                    |
| Parallelism needed | Match to max expected concurrency                    |
| Hardware capacity  | Keep under 20,000 partitions per broker cluster-wide |

**Example:**
If you expect 1 million events/second:

* Target **\~1,000 to 5,000 partitions**
* Deploy **1,000 to 5,000 consumer threads** (or more if using batching)

---

### 🔸 Important Notes

* Kafka **doesn't auto-scale partitions** — you must define and manage them.
* **More partitions ≠ always better**. Balance between:

  * Throughput
  * Latency
  * Storage/replication cost
  * Consumer complexity

---

### Summary

> 🔹 Using `paymentId` as the partition key with 1 million messages/sec **does NOT create 1 million partitions**.
> 🔹 Instead, **Kafka hashes the `paymentId` and maps it to one of the fixed partitions** (say, 1000).
> 🔹 You decide the number of partitions when creating the topic based on desired **throughput and parallelism**.
